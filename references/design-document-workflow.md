# 解析并使用系统设计文档

适用于 `design.md`、`DESIGN.md`、`WE_design.md` 等结构化或叙述式设计规范。目标是把文档转换成可追溯的生成依据，而不是仅阅读后凭印象写 CSS。

## 1. 识别文档结构

1. 确认文档所属系统、版本、适用端和目录。多份文档先按系统归组；同名色值不能跨系统合并。
2. 若文件以 `---` 开头，按 YAML frontmatter 解析到下一条单独的 `---`。识别 `colors`、`typography`、`rounded`、`spacing`、`components` 等嵌套字段；`name`、`description`、`version` 等是元数据。不要假设所有文档都有完整的令牌 YAML。
3. 扫描正文标题、表格和条目，提取全局框架、列表、筛选、表格、表单、弹窗、抽屉、交互状态和响应式规则。正文中的具体页面规则可能比全局令牌更窄，必须保留适用范围。
4. 查阅 `Revision Notes`、`Known Gaps`、`未观测到`、`推断` 等标记。把已验证、继承默认、推断、未知分开；未知处不得伪称来自规范。

## 2. 解析令牌与解决冲突

- 保留原始令牌路径和值，如 `colors.primary`、`components.filter-bar.labelWidth`。遇到 `"{colors.primary}"`、`"1px {colors.border}"` 等引用时递归解析后再写 CSS；发现缺失路径或循环引用时停下该项并记录，不要将 `{...}` 原样输出。
- 同一概念可能在不同范围取不同值，例如“表单标签宽度”和“筛选栏标签宽度”。先按组件和页面范围匹配，再谈冲突；不要拿全局值覆盖更具体的规则。
- 正文、YAML、修订记录、实际项目代码出现不一致时，比较版本、适用范围和证据性质。用户指定的权威来源优先；明确修订后的同范围规则优于旧值。仍无法确定的项在映射说明中列出选择依据。
- 若文档只有文字或表格而没有 token map，仍要抽取显式值；没有值的项目从实际仓库主题/组件实现查找，再退到相应组件库默认值。每次回退都标明来源。

## 3. 把规则落到 HTML

生成前建立一张简表，最少包含下列列；不要求写成固定格式的中间文件：

| 规则 | 来源 | 适用范围 | 解析结果 | 输出位置 | 组件对应 |
| --- | --- | --- | --- | --- | --- |
| 主色 | `design.md` frontmatter `colors.primary` | 全局按钮/链接 | 具体色值 | `--color-primary`、按钮/链接 CSS | Button |
| 筛选栏标签宽度 | `design.md` 的 `filter-bar` 规则 | 列表筛选 | 具体宽度 | 列表筛选项 CSS | Form.Item / 自定义筛选组件 |
| 弹窗内容滚动 | `design.md` 的 Modal 小节 | 弹窗 | 头尾固定、内容滚动 | 弹窗结构与 CSS | Modal |

- 共享令牌先落为 CSS 自定义属性，再用于具体组件；组件专属值留在组件规则中。不要把“只有某个页面才适用”的行为提升为全局变量或所有模板的默认行为。
- 框架/组件库决定该系统实际使用哪些组件及状态。静态 HTML 用语义元素与 CSS/JS 复现其可见结构和演示交互；在映射说明中写明对应的 React/Vue/组件库组件，避免声称静态 HTML 已调用这些组件。
- 每个模板完成后反查映射：来源规则是否真的被应用；CSS 中是否有无来源的关键颜色/尺寸；是否遗漏了页面专属布局或状态。

## 三种输入结构的检查示例

以下只说明解析方法，不是其他系统的默认设计值：

- Market W+ 的 `design.md` 在 YAML 中给出 `colors.primary: #1774FF`，并在 `components.filter-bar` 中给出筛选布局。正文进一步限定列表为连续白色工作区、表单页可有不同宽度。解析时应同时使用令牌与页面规则。
- WE 的 `WE_design.md` 在 YAML 中给出 `colors.primary: #5D79FF`、`components.form-label-width: 120px`；正文把筛选栏标签限定为 96px。两者属于不同组件范围，不能只取一个值给所有标签。
- 财富 w+ 的 `DESIGN.md` frontmatter 主要是元数据；具体颜色、Ant Design 5、Less CSS Modules 等在正文表格与叙述里。只读 YAML 会漏掉真正的设计规则。
